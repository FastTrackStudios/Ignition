# Venue: Rockstars of Tomorrow, Riverside CA

Unlike [`norco`](../norco/), this venue is **measured, not extracted** — there
is no Eos show file to derive it from, so every file here is generated by
[`tools/build_riverside_venue.py`](../../../tools/build_riverside_venue.py)
from the operator's tape readings and the room photos. **Edit the constants
at the top of that script and re-run it; do not hand-edit the JSON.**

```sh
python3 tools/build_riverside_venue.py

# look at it
cargo run -p ignition-viz --bin viz -- --venue data/venues/riverside \
  --exclude Ceiling --eye 0,-6.8,1.9 --look 0,1.2,1.6

# drive it from the studio
IGNITION_VENUE=data/venues/riverside cargo run -p ignition-studio
```

| File | Contents |
|---|---|
| `fixtures.json` | 39 fixtures across three positions — see below |
| `room.json` | 13 objects — stage deck, lip, house floor, four walls, beam, ceiling, four light poles |
| `groups.json` | 19 groups — per-pole, per-row, per-position, and the two the profile binds to |
| `palettes.json` | 11 focus points. **No colours** — those are inherited from the profile |
| `profile.json` | binds Riverside's groups to the `Ignition` profile's portable roles |
| `areas.json` | the six-area blocking grid |
| `props.json` | 19 — the band, their gear, PA and wedges, disco ball, the arch |
| `patch.json` | **provisional** DMX patch — 39 fixtures, one universe. The one file here the generator does not own |
| `screens.json` | empty — no video surfaces modelled yet |

Coordinate convention is identical to the Norco extract, so both venues load
through the same `ignition_viz::venue::Venue`: **+X stage left, +Y upstage,
+Z up, metres**, origin at the centre of the stage deck **at deck level** —
so the room floor is at `z = -0.508`.

Every number in the generator sits in one of three tiers, each labelled in
the source: **MEASURED** (the tape — trust it), **PHOTO** (counted off the
room photos — plausible, and the first thing a real patch list should
overwrite), **ASSUMED** (neither measured nor visible — a working value).

## The rig

Channel blocks are left with gaps between positions so a real patch can land
without renumbering everything downstream of it.

| Chans | Position | Fixtures | Tier |

| 17–20 | Back wall, pole tops | 4 movers | measured |
| 21–23 | Back wall, top | 3 bars | measured |

| 37–38 | House beam | 2 amber strips | photo |
| 41–48 | Back-of-house wall | 7 pars (3 + 4 flanking the arch) + 1 above | photo |

```
   11' 8"  ── ▭▭▭▭▭   ▭▭▭▭▭   ▭▭▭▭▭      3 bars           21–23
   11' 3"  ── ◆        ◆        ◆        ◆   4 movers      17–20
   10' 4"  ── ●        ●        ●        ●   par row 4     4,8,12,16
    8' 4"  ── ●        ●        ●        ●   par row 3
    6' 4"  ── ●        ●        ●        ●   par row 2
    4' 4"  ── ●        ●        ●        ●   par row 1     1,5,9,13
    0' 0"  ══╧════════╧════════╧════════╧══  stage deck (20" up)
              │←─ 64" ─→│←─ 64" ─→│←─ 64" ─→│
              pole 1    pole 2    pole 3    pole 4
              ←──────── house left to right ────────→
```

Those heights are the measured spacing (40" to the lowest par, 2' between
rows) plus **`BACKWALL_LIFT`**, currently 1' 0" — the operator's call after
seeing the first model: the rig read low in the room. It is one constant, and
everything on that wall moves with it, poles included, so the measured
spacings stay in register no matter what it is set to. The poles grow rather
than float; their base stays on the deck. There is 1.88 m of clearance
between the bars and the house beam, so there is room to keep going.

Fixture orientation is the **hang**, per
[`docs/domain/norco-venue-reference.md`](../../../docs/domain/norco-venue-reference.md).
For a fixed par or bar the mount angle *is* the aim, so the generator solves
it from a target point — the same statement as writing the angle down. The
movers never go through that: their hang is base-down on a pole top (a 180°
flip), and pan/tilt is live show data, not placement.

## The band

Where people actually stand, per the operator. They described it from the
**audience's** side of the room — "back left corner", not "upstage right" —
so `left` here means house left, which is stage right, which is `-X`.

```
        ┌──────────────── upstage wall ────────────────┐
        │  DRUMS          GUITAR           KEYS        │   back line
        │                                              │
        │  BASS           VOCAL                        │   front line
        │  ▓PA                                    PA▓  │
        └───────────── stage lip / house ──────────────┘
           house left        centre        house right
           (-X, stage R)                   (+X, stage L)
```

The palette keeps the *stage's* own naming, because that is what a desk
says — the bass player at house left stands on `Vocal Stage Right`. Each of
the five positions therefore has two focus points:

| Grid name (a place) | Band name (a person) |
|---|---|
| `Upstage Right` | `Drums` |
| `Upstage Centre` | `Guitar` |
| `Upstage Left` | `Keys` |
| `Vocal Stage Right` | `Bass` |
| `Vocal Centre` | `Lead Vocal` |

Both sets are wanted. The grid is where a *position* is and survives the band
changing; the band names are what an operator calls for when busking ("hit
the keys"), and move when the band re-blocks. `Drums` is the one that is not
simply an alias — it points at the kit, which sits lower and further into the
corner than the drummer does.

The **PA mains are not on the stage**: they stand on the room floor in front
of the lip, on tripods, cabinets flown at 1.80 m. Their record therefore sits
at `FLOOR_Z` and `props::Stand::Tripod` lifts the cabinet, so `size.z` is the
cabinet's own height rather than how high it ends up. Being off the deck they
also sit wider than the stage — the room is 21' across where the stage is
19' 8".

The keyboard, the PA cabinets and the four monitor wedges are real models
(CC-BY, see `crates/ignition-viz/assets/props/LICENSE-NOTICE.txt`), seated by
`props::GLB_PROPS`. The keyboard is scaled by its **length**, not its height:
the model is the instrument alone, its music rest is twice as tall as its
body, and fitting it by height gives a keyboard four metres long. It stands
on the deck and `props.rs` draws an X-stand under it to lift it to playing
height — four primitives, the same call the mic stands make.

The kit is held 18" off the back wall on purpose: the light poles stand on
the deck, and a kit pushed flat against the wall has pole 1 coming up through
the floor tom.

## Profile

Riverside implements the `Ignition` profile. The binding lives in
`profile.json`; `cargo test -p ignition-core --test profile_binding` checks
it — and now checks *every* venue under `data/venues/`, not just Norco.

| Role | Riverside group |
|---|---|
| Key | `FOH Pars` |
| Wash | `Beam Pars` |
| Back | `Back Wall Pars` |
| Movers | `Movers` |
| Bars | `Strips All` |

`palettes.json` deliberately declares **no colours**. `venue::inherit_colors`
fills them from the profile, so Riverside means the same thing by "Deep Blue"
as every other room until it has a reason not to.

Roles with nothing to bind to here: `Beams` (no hard-edged package), `Floor`
(no uplight), `Audience` (no blinders), `Drums` (no special), `Haze`, `Spot`,
and all three canvases (no screens). None are required.

## Patch

The desk is a **myDMX 5 / Daslight 5** rig (interface: myDMX 3, serial 781584),
one universe, 57 fixtures, 419 of 512 channels, no overlaps.

`.dvc` is not opaque. It is plain XML rooted at `<DLMFILE TYPE="Daslight"
VERSION="5">`, with the bulk payloads packed into ordinary attributes as
`base64( uint32be(uncompressed_length) + raw zlib )` — a few smaller ones
hex-encoded, same container. Fixture profiles are embedded inline, so a
showfile is self-contained: the `.ssl2` library files are not needed to
recover a channel map.

[`tools/dvc_parse.py`](../../../tools/dvc_parse.py) reads it, **read-only** —
it never writes to the showfile and never talks to the desk:

```sh
tools/dvc_parse.py "Gearbox Lighting 5.0.dvc" --json data/venues/riverside/console-show.json
tools/dvc_parse.py "Gearbox Lighting 5.0.dvc" --dump out/    # every payload, decoded
```

`console-show.json` is the committed extract: 57 fixtures (address, universe,
footprint, type, and the desk's 2D stage-view `posx`/`posy`), 12 fixture
profiles with their exact channel layouts, and the 13 groups.

### The inner schema, and the trap in it

```
PATCH NBFIXTURE=57
  FIXTURES                                  one block per fixture type
    SSLLIBRARY SSLNAME="_varied/Solena Professional Max Par 54 RGB.ssl2"
    SSLMODES > SSLMODE SSLNBCHANNEL=7
               > SSLCHANNEL SSLCHANNELNAME="Dimmer" SSLCHANNELTYPE=7 ...
    FIXTURE NAME=... ADDRESS=250 UNIVERS=1 POSX=430 POSY=-230
```

**Document order is the DMX offset.** `SSLCHANNELTYPEINDEX` looks like an
offset and is not — it disambiguates several channels of the same type (a
profile with two macro channels has type 0 index 0 and type 0 index 1).
Reading it as an offset silently scrambles every map. `SSLCHANNELMSB` /
`SSLCHANNELLSB` are flags marking the coarse and fine halves of a 16-bit
pair, not numbers.

`SSLCHANNELTYPE` is a semantic code, which is what makes the extract
mechanically convertible into `ignition_viz::channel_map` entries:
1=Pan, 2=Tilt, 7=Dimmer, 8=Gobo, 15=Strobe, 18=Speed, 22=Lamp, 24=Pump,
25/26/27=RGB, 31=White, 37=Macro, 43=Warm White, 0=untyped. One profile
(MINI DERBY) types every channel 7; there, the names are the only truth.

### Which fixture is where

The desk's 2D stage view settles the ordering the group list alone does not.
The `WALL` block is a 4x4 grid — POSX 430/490/550/610 (four poles, house left
to right) by POSY -230/-190/-150/-110 (four rows, top to bottom):

```
   POSX      430  490  550  610     <- pole 1..4
   POSY -230 250  278  306  334     <- par row 4 (top, 9'4")
        -190 257  285  313  341     <- row 3
        -150 264  292  320  348     <- row 2
        -110 271  299  327  355     <- row 1 (bottom, 3'4")
```

Address ascends *down a pole*, then moves to the next pole. The group lists
`WALL` **row-major** while the patch runs **pole-major** — reading either as
the other transposes the grid, so a chase meant to sweep across the poles
would instead run up and down one.

`posx`/`posy` are schematic, not metric: the operator arranges icons to look
like the room, and the movers are drawn far wider apart than the poles they
actually sit on. Trust them for order and grouping, not for distance.
